The Surprisingly Non-trivial Problem of Building Verifiable Evaluation Methods for Agent Simulations

#shorts

Verifiable rewards can feel fairly easy. When you ask an agent to change something in a database, if it does so, it should be rewarded; if not, it should not. Verifiable outcomes seem simple, right? Having spent the past several months designing evaluation simulations, I can tell you: in practice, things get weird.

The core problem is that the same outcome can be completely valid or completely invalid depending on the trajectory. Take a flight-booking task. If the agent tells you it booked the flight, should it get credit? Not necessarily. The agent may have called the booking endpoint, received a 500 error, and then confidently reported success anyway. The surface-level outcome looks identical; the underlying reality is not. Verification has to take into account the entirety of the end state.

Here are the design principles I've been building into my evaluations:

  1. Try to cast your evaluations in a verifiable way. While LLMs-as-a-judge may seem simple at first, you trade off simplicity for accuracy of your evaluation measure. This is especially true if you want your LLM to evaluate on a rating scale. Think hard about whether there's a way to grade in a verifiable manner before resorting to LLMs-as-a-judge.
  2. Think in verifying trajectories, not just outcomes. In predictive ML, you have confusion matrices and false positive/negative breakdowns. In multi-step agentic ML, the equivalent is mapping the distinct states an agent can land in at each decision point, then labeling each state as SUCCESS or FAIL. Rather than asking "did it succeed?", you ask "which states did it visit, and how often?" — which gives you a much richer diagnostic picture.
  3. Make your environment as clean as possible to isolate what you are measuring. If you're evaluating an agent's ability to execute on an ambiguous PRD, make sure any user simulators in the loop are well-behaved (within the constraints of what is realistic, of course). Noisy simulators introduce unnecessary complexity into the end-state space, and when it's time to assign credit, you'll struggle to tell whether a bad outcome reflects agent failure or environment noise.
  4. Work backwards from the steel-thread outcome. Given the final artifact in isolation — a response, a database change, a produced file — ask yourself: are there paths that could produce this artifact through invalid means? If a technically correct-looking output could result from a shortcut, a hallucinated step, or an error that got swallowed, your verifiers need to account for it.

Aside from building agent evaluations from scratch, I've also had some learnings on adopting a new publicly released agent benchmark, given the amount of issues on current simulations (e.g. SWE-Bench Verified, Tau3-bench corrections for Tau2-bench).

  • If all rollouts for a particular trajectory do not pass, especially for more than one ML system, then that task may be underspecified (e.g. impossible to do given the context available/reachable in the environment and task).
  • Github issues are always helpful. Look at them before starting to setup and reproduce the evaluation.
